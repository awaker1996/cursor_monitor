# 聚合接口「空窗口」诊断与端点收敛

- 日期：2026-11-01
- 类型：fix
- 关联文件：src/core/providers/CookieProvider.ts、scripts/verify-cookie-summary.ts、README.md

## 背景与日志证据

用户实测日志（2026-10-31 23 时后）：

```
[CookieProvider] Aggregated usage endpoint returned unusable response {
  endpoint: 'https://cursor.com/api/dashboard/get-aggregated-usage-events',
  teamId: 0, hasUserId: false, status: 200,
  contentType: 'application/json; charset=utf-8',
  redirect: null,
  bodyPreview: '{"startDate":"1792835666000"}',
  error: null
}
[CookieProvider] ... endpoint: 'https://www.cursor.com/...',
  status: 308,
  redirect: '接口返回 308 重定向到 https://www.cursor.com/api/dashboard/get-aggregated-usage-events',
  bodyPreview: '{"redirect": "...", "status": "308"}'
```

## 根因分析

1. **不是网络问题、也不是 Cookie 过期**：请求拿到 200，鉴权层没有拦截（过期会是 401，或 307 跳 WorkOS 登录）。
2. `{"startDate":"1792835666000"}` 是服务端「窗口内没有可聚合行」的形态——原样回显窗口起点、不带 `aggregations`。而账单周期起点与本地缓存一致（`1792835666000` = 2026-10-24T09:54:26Z），说明窗口本身没算错。
3. `hasUserId: false` 是关键线索：`usage-summary` 能正常返回，但 Cookie 里解析不出数字 `userId`。dashboard 的明细接口按 `userId` 过滤，缺了它服务端只回一个空窗口，于是 Included Usage 恒为空、周期 token 明细只能靠事件接口的分页聚合兜底。
4. `www.cursor.com` 对 dashboard POST 返回 **308 且 Location 指回自身**（自我重定向），该备用端点彻底失效；旧代码仍每轮为它发两三次请求（含网络重试）。

## 变更摘要

- 事件 / 聚合端点收敛为只用 `cursor.com`，移除 `www.cursor.com`（汇总端点仍保留 www 兜底）
- 聚合请求新增**日期编码探测**：`ms-number` → `ms-string` → `iso` 逐个尝试，成功的编码记入模块级 `preferredDateEncoding`，后续刷新优先复用；每种组合的失败日志都带 `encoding` 与 `hint`
- 新增 `describeAggregatedPayload()`：把「200 但没有 aggregations」归类为
  `空聚合窗口：只回显 startDate，服务端没有返回任何模型行` / `响应字段：...` / `空对象响应`
- 新增 `describeCookieShape()`：`userId` 解析失败时输出 Cookie 形态（有无 `WorkosCursorSessionToken` 前缀、是否 `::` 分隔、JWT 段数、`sub` 是数字/带前缀/缺失、长度），日志不含任何密文
- 新增回归断言：Cookie 三种形态归类、三种日期编码、空窗口 payload 归类

## 影响范围

- Cookie 链路每轮请求数：聚合从最多 4 次降到成功路径 1 次；全失败时最多 6 次（2 个 teamId × 3 种编码）后返回 null，Included Usage 回退事件聚合
- 事件端点失去 www 备用（该备样本就不可用）
- 汇总端点与官方链路未改

## 验证

- `npm run typecheck` 通过
- `scripts/verify-cookie-summary.ts`（含 8 条新增断言）、`scripts/verify-today-percent.ts`、`scripts/verify-included-usage.ts` 全部通过
- `npm run build` 通过

## 待观察

新的日志会直接给出两种结论之一：若某一日期编码成功 → 自动复用，Included Usage 恢复；若仍全部为空窗口且 `describeCookieShape` 显示 `jwtParts: 0` 或 `subKind: prefixed`，说明当前 Cookie 是不含数字 `userId` 的新式会话令牌，需要重贴带 `userId::jwt` 形态的 Cookie（或后续从账号接口补齐 userId）。

## 追加（同日第二轮）

实测第二轮日志：`ms-string` 仍是 200 空窗口，`iso` 直接 500（服务端只认毫秒时间戳）。据此补两项：

- **编码探测收敛**：一种编码只要拿到 2xx JSON 就判为「服务端接受」，不再换编码（不再产生 500 噪音）；实测每轮聚合请求从 6 次降到 2 次（teamId -1 / 0 各一次）
- **userId 兜底补齐**：Cookie 解析不出数字 userId 时，先请求 `https://cursor.com/api/auth/me`（未登录实测 204，登录后应带用户对象），用 `extractNumericIdFromPayload()` 从 `id` / `userId` / `user.id` 里取数字 id；成功后缓存，失败冷却 10 分钟再试
- 聚合全部失败时补一条总结日志「Included Usage 聚合不可用，回退事件聚合」，并区分「缺 userId」与「窗口内无可聚合行」
- 新增 `extractNumericIdFromPayload` 的 5 条回归断言
